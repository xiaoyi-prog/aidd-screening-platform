# 数据模型设计说明

本文记录三层架构的具体落地决策，配合 `migrations/` 一起看。目标是把"可复现、可追溯的筛选流水线"变成表结构上的硬约束，而不是靠流程约定。

---

## 一、总体原则

1. **不覆盖，只追加**：ODS 层保留每批快照；DWD 层用业务唯一键 + `ON CONFLICT` 收敛；ADS 层按 `run_id` 隔离。
2. **每个数值都能自证**：性质值必须带单位、值类型（实测/计算/预测）、方法或模型版本。
3. **每个结论都能倒推**：任何筛选结论都能沿 `stage_trace → lineage_event → batch_id` 回到原始报文。
4. **配置进库，不进代码**：阈值、权重、功能规格窗口、法规限值都是数据行，改配置不用发版。

---

## 二、ODS 层

### 2.1 统一审计列

所有 ODS 表都有四列：

| 列 | 作用 |
|---|---|
| `batch_id` | 指向 `meta.fetch_batch`，把"这批数据什么时候、用什么参数抓的"钉死 |
| `ingested_at` | 入库时刻，用于排查延迟 |
| `src_row_hash` | 源记录内容的 sha256，用于增量比对：哈希没变就跳过，省一次全量 upsert |
| `raw_payload` | 原始报文（JSON），解析逻辑升级后可整批重解析，不用重新抓 |

### 2.2 表清单与选型理由

| 表 | 说明 |
|---|---|
| `ods.pubchem_compound` | 结构与基础描述。PubChem 的 CID 是外部主键，批内唯一 |
| `ods.pubchem_property` | PUG-View 的属性是深嵌套、异单位的，硬拆列会丢信息，所以用长表 + `raw_payload` |
| `ods.pubchem_synonym` | 辅料大量使用俗称/商品名（如"吐温 80"），必须有别名表 + trigram 索引 |
| `ods.pubchem_classification` | MeSH 分类是判断"是不是辅料/高分子"的可用信号 |
| `ods.chembl_molecule` / `chembl_activity` / `chembl_assay` / `chembl_target` | 活性数据的金标准；`assay` 与 `target` 单独拆出，因为活性值可信度取决于测定方法与靶点质量 |
| `ods.drugbank_drug` / `drugbank_target` | 药物-靶点-相互作用，XML 展平后仍保留整节点 |
| `ods.fda_iid_entry` | 该辅料出现在哪些已批准制剂/途径 → "已上市可接受性"证据 |
| `ods.fda_iig_limit` | 按途径-剂型的最大用量 → **安全边际的分母**，三级深筛的核心输入 |
| `ods.internal_excipient_spec` | 供应商 COA、级别、价格、交期 → 五级放大评估 |

> 为什么把 FDA IID/IIG 放进 ODS？因为公司做的是药用辅料，法规证据链和结构数据一样重要，且它们的更新节奏、许可条款与 PubChem 完全不同，必须独立成批。

## 三、DWD 层

### 3.1 dim_compound：以 InChIKey 为唯一键

```
inchikey            text (DOMAIN: ^[A-Z]{14}-[A-Z]{10}-[A-Z]$)  UNIQUE
inchikey_skeleton   generated: split_part(inchikey,'-',1)      -- 骨架，14 位
parent_compound_sk  self FK                                     -- 盐型挂到母体
is_desalted_parent  boolean                                     -- 是否去盐后的母体
compound_class      small_molecule | polymer | oligomer | lipid | inorganic | peptide | other
structure_quality   valid | suspect | invalid                   -- 质量闸门，不删除只标记
```

**为什么用 DOMAIN 做格式校验**：InChIKey 格式错误是"化学标准化被绕过"的典型症状（例如直接把 SMILES 字符串塞进去）。在类型层拦住，比在 ETL 里写 if 更可靠。

**去盐策略**：RDKit `MolStandardize` 的 `LargestFragmentChooser` + `Uncharger` 产出母体，
母体与盐型都入库（盐型 `is_desalted_parent = false`，`parent_compound_sk` 指向母体）。
理由：处方里用的是盐型（硬脂酸镁不能用硬脂酸替代），但筛选和聚类要按母体归并，两者都不能丢。

### 3.2 fact_property：长表 + 三元定位

```
(compound_sk, property_code, value_type, source_system, model_code, model_version, temperature_c, ph)  UNIQUE
```

这 8 个字段组成业务唯一键，唯一索引用 `COALESCE(...,'')` 处理 NULL，保证：

- 同一性质可以有 `measured` / `predicted` / `computed` 三份，互不覆盖；
- 两个模型预测同一个性质，各自留档，可做模型对比；
- 不同温度/ pH 下的实测值（如 pH 依赖的溶解度）分别成行；
- ETL 重跑幂等。

`qualifier` 字段处理 "> 300 °C 分解" 这类没法精确测的记录，避免为了填数值而造假。

### 3.3 fact_activity

外部唯一键 `(source_system, source_record_id)`，保证 ChEMBL 的 activity_id 不会被重复导入。
保留 `is_potential_duplicate`、`data_validity`、`quality_score` —— 活性数据里重复与低质量条目极多，
清洗规则应该可配置、可回溯，而不是在 ETL 里一刀切删掉。

### 3.4 fact_compatibility（辅料业务特有）

API × 辅料 × 条件（比例/温度/湿度/时长）→ 稳定性结果。
这是"配伍深筛"的证据源，也是公司最容易积累的独家数据（湿实验做一次很贵），
所以单独成表而不是塞进 `fact_property`。

### 3.5 bridge_compound_function

分子 ↔ 功能角色多对多（PVP 既是黏合剂又是增溶剂），带 `is_primary` 与置信度。
二级筛选的候选集就是从这里按功能反查出来的。

### 3.6 dim_excipient_grade

同一化合物不同级别性能差异极大（HPMC E5 vs E15），价格与供应也不同。
五级放大评估必须落到"某个供应商的某个级别"，所以级别独立成维。

## 四、ADS 层

### 4.1 screen_run：一次 run 冻结三件事

```
model_snapshot   {"PROP_MLP":"v1.3.0","TOX_ADMET":"v3.1.2"}   -- 模型版本
funnel_config    {...}                                        -- 全局配置
code_version     "aidd-pipeline@2.3.1"                        -- 代码版本
```

`run_stage_config` 再存每级的 `thresholds / weights / filter_rules`。
同一个候选集可以用两套参数跑两个 run 做 A/B，互不干扰。

### 4.2 candidate_pool：漏斗台账

`(run_id, compound_sk)` 主键，`status ∈ (in_funnel, advanced, hold, rejected, shortlisted)`。
五级快照表都用复合外键指向它，因此：

- 不能出现"三级有分但候选池没这个人"；
- 淘汰要写 `exit_stage` + `exit_reason`，漏斗转化率有唯一口径。

### 4.3 五级快照表

每级一张表而不是一张大表，原因是各级判据差异大：

- 一级字段是预测概率与类药性描述符；
- 二级是物性与规格窗口的逐项匹配；
- 三级是安全边际与配伍；
- 四级是对接与 MD 指标；
- 五级是成本与供应。

合表会产生大量 NULL 与含义漂移的复用列（比如 `score1..score5`），后期无法维护。
代价是五张表，收益是每张表的字段都能自解释。

### 4.4 compound_score：可解释性

```
(run_id, compound_sk, stage_no, score_code) PK
score_value 0-100, weight, weighted_value (generated)
model_code, model_version, rationale
```

为什么要长表：研发一定会问"为什么它排第 3"。
长表能直接答"因为 FUNCTION_FIT 92 分、权重 0.6；TOX_RISK 只有 55 分、权重 0.3"，
而宽表 + 加权总分只能给出一个黑箱数字。

### 4.5 rank_result 与 stage_trace

- `rank_result`：结论层，含 `verdict ∈ (recommend, conditional, hold, reject)` 与人工复核痕迹
  （`reviewer` / `reviewed_at`）—— 湿实验前的最后一道人审必须有记录。
- `stage_trace`：过程层，每次 pass/reject/override 都写一条，带输入/输出快照与哈希。
  复现争议时按 `run_id + compound_sk + stage_no` 就能回放。

## 五、META 层

### 5.1 fetch_batch

`(source_code, snapshot_label, source_release, request_params, checksum_sha256)`。
`request_params` 记录抓取时用的 URL 参数/查询语句，这是"同批次可重放"的前提。

### 5.2 etl_run

记录 `code_version`、`container_image`、`params`、读写/拒绝行数。
一句话：**同一个 run 换台机器也应该得到同样的结果**，前提是这些都被记下来。

### 5.3 lineage_event（按月分区）

```
PARTITION BY RANGE (occurred_at)
```

- 预建 3 个月分区（`meta.fn_roll_lineage_partitions`），并有 `BEFORE INSERT` 触发器兜底自动建分区；
- `entity_key` 统一用 InChIKey（分子）或 `run_id:compound_sk`（候选），便于跨层 join；
- `input_hash` / `output_hash` 用来判断"重算是否产生差异"，比逐字段 diff 便宜。

分区而非单表的理由：血缘是只增不减的流水，量级会远大于业务表，按月分区后归档一条 `DROP PARTITION` 搞定。

### 5.4 数据质量门禁

`data_quality_rule.expression` 是一段返回违规行数的 SQL。
把规则做成数据行，好处是业务同学能自己加规则（例如"注射剂辅料必须有安全边际"），不用等发版。

## 六、刻意没做的事（以及为什么）

| 没做 | 原因 |
|---|---|
| 不用 `CREATE TYPE ... AS ENUM` | 枚举加值要 DDL，迁移成本高；用 `text + CHECK` 同样有约束，改动更轻 |
| 不给 `fact_activity` / `fact_property` 分区 | 目前量级（万级分子 × 十级性质）用 B-tree 足够；等 PubChem 全量进来再按 `created_at` 分区，届时唯一索引需带上分区键，方案要重新设计 |
| 不建 `dim_date` | 分析全部基于 `timestamptz`，没有按自然日历汇总的需求 |
| 不用外键 `ON DELETE CASCADE` 连锁删业务表 | 除候选池这类 run 派生数据外，主数据一律 `RESTRICT`，防止误删穿透 |
| 不把 SMILES 存成 RDKit `mol` 类型 | Windows 官方包无 rdkit cartridge；结构检索走应用层，库内以 InChIKey 为准 |

## 七、后续演进

1. **高分子辅料建模**：`compound_class = 'polymer'` 已预留，需要设计重复单元（`[repeat]`）、分子量分布、端基等字段，建议单开 `dwd.dim_polymer` 与 `fact_polymer_property`，不要硬塞进 `dim_compound`。
2. **实验数据回流**：`dwd.fact_property` 的 `value_type = 'measured'` 已支持，需要补一张 `dwd.fact_experiment`（实验号、仪器、操作人、原始文件指针）。
3. **pgvector**：分子指纹/描述符向量检索（相似辅料推荐），加 `vector` 扩展后新增 `dwd.compound_embedding`。
4. **物化视图刷新调度**：目前靠 ETL 显式 `REFRESH ... CONCURRENTLY`，后续接 pg_cron 或编排器。
